🛡️ Resilient Power Query

The monthly report is mostly the same. A column gets renamed, the title block gains a row, someone adds a "Notes" field, a total row creeps in at the bottom. Your query breaks — or worse, it doesn't break and quietly returns the wrong number. This lesson is the set of habits and recipes that make a query survive next month's file.

💣 Why last month's query breaks this month

Power Query records what you clicked, not what you meant. You meant "keep the sales figure"; it recorded "keep the column literally called Net Sales, which is the 4th one". Next month it's called Sales Amount and it's the 6th. The recording is now a lie, and the query either errors or silently drops the column.

A brittle query says

"Skip 4 rows. Take columns 1, 3 and 7. They are called exactly this. Every value converts cleanly. Region is one of these five values."

→
A resilient query says

"Find the row containing Order ID. Give me these six fields under whatever name they arrive; invent them as blank if missing. Anything that won't convert, park it for me to look at."

The dangerous half of that table

Rows that error are the lucky ones — you find out immediately. The killers are the silent ones: a frozen filter that drops a new region, an added column that shifts your data, a date parsed in the wrong locale. Those refresh green and hand you a number that is wrong by exactly enough to be believable. Everything in this lesson exists to convert silent failures into loud ones.

🏗️ Build it in four queries, not one

A single 40-step query is impossible to debug when it breaks at step 27. Split the work so that each query has one job, and so that when the source changes there is exactly one place to fix it.

1 · Parameters

Folder path, file name, reporting month, cut-off date. Home → Manage Parameters. Nothing about where the data lives should be buried in a step.

2 · Raw (connection only)

Connect and stop. No transformations at all — this is the "what did they actually send us" query you click when something looks wrong.

3 · Clean (connection only)

All the defensive work: anchor headers, alias, pin schema, drop junk rows, set types. Ends with a table whose shape you can guarantee.

4 · Output (loaded)

Business logic only: filters, calculated columns, grouping. Because Clean guarantees the shape, nothing here ever needs touching when the source wobbles.

How to make a query "connection only"

Home → Close & Load To… → Only Create Connection. Or afterwards: right-click the query in the Queries & Connections pane → Load To…. Intermediate queries should never land on a sheet — they clutter the workbook and slow the refresh.

Reference, don't duplicate. Right-click a query → Reference creates a new query that reads the output of the first. Duplicate copies all the steps, so a fix has to be made twice. If you ever find yourself fixing the same step in two queries, you used Duplicate when you wanted Reference.

Rename every step, in plain English

Right-click a step → Rename. Removed junk rows and totals tells the next person (you, in April) what the intent was. Filtered Rows2 tells them nothing. When a query breaks, well-named steps cut the debugging time roughly in half.

📌 Pin the schema — the single most valuable trick

One line of M solves four of the eleven failure modes at once. Instead of removing the columns you don't want, declare the columns you do want — and tell Power Query what to do when one is missing.

Table.SelectColumnsLearn this one properly
Table.SelectColumns(table, {"names"}, missingField)
  • table the table coming out of the previous step
  • {"names"} the exact columns you want, in the order you want them
  • missingField what to do when a listed column isn't there
// The default: blow up if anything is missing
Table.SelectColumns(Source, {"Order ID", "Region", "Sales"})

// Skip it silently — column simply won't exist downstream
Table.SelectColumns(Source, {"Order ID", "Region", "Sales"},
                    MissingField.Ignore)

// Create it, full of nulls — output shape never changes  ⭐
Table.SelectColumns(Source, {"Order ID", "Region", "Sales"},
                    MissingField.UseNull)
OptionColumn missing →Use it when
MissingField.Error (default)Query fails loudlyThe column is essential — you'd rather stop than publish a report without it
MissingField.IgnoreColumn just isn't in the outputOptional extras, and for renames (below)
MissingField.UseNullColumn appears, filled with nullThe default choice. Downstream steps, pivots and formulas keep working; blanks show you what was missing

✅ Fixes: added columns

A new Notes field appears in the export? It isn't on your list, so it never enters your query.

✅ Fixes: reordering

The output is in your listed order, whatever order the source used.

✅ Fixes: missing columns

With UseNull, the column exists anyway. Your pivot doesn't lose a field; your formulas don't return #REF!.

Where to type this

You don't have to write M from scratch. Click the columns you want → right-click → Remove Other Columns. Power Query writes Table.SelectColumns(Source, {…}) for you. Then click that step and, in the formula bar, add , MissingField.UseNull before the closing bracket. Two seconds of typing, four failure modes gone.

No formula bar? View → Formula Bar. Turn it on permanently — you'll use it constantly from here on.

Handling the renames: an alias list

Pinning the schema only works if the column is called what you expect. Deal with the source's favourite variations first, then pin. Table.RenameColumns takes the same MissingField argument, so you can list every alias you've ever seen and only the ones present get applied.

// Rename first — list every alias the source has ever used
// MissingField.Ignore means unused aliases are simply skipped
Table.RenameColumns(Source, {
    {"Cust ID",       "Customer ID"},
    {"Customer Id",   "Customer ID"},
    {"CustomerNumber","Customer ID"},
    {"Net Sales",     "Sales"},
    {"Sales Amount",  "Sales"},
    {"Amount (GBP)",  "Sales"}
}, MissingField.Ignore)
One trap with alias lists

If two aliases for the same target turn up in the same file — say both Net Sales and Sales Amount — the rename fails with There were duplicate column names. That is the correct behaviour: you genuinely don't know which one is the real figure. Open the Raw query and look before you decide.

The grown-up version: an alias table on a worksheet

Once you have more than a handful of aliases, stop editing M. Put a two-column Excel Table called HeaderAliases on a sheet in the workbook and drive the renames from it — then a colleague can add next month's variation without opening the editor.

🎯 Headers that move and headers that lie

Problem 1: the title block grows

Exports love a preamble — a logo row, a "Report generated 03/02/2026" line, a blank row, then the headers. Power Query records Table.Skip(Source, 4). Next month there's a new subtitle and your headers become Column1, Column2, Column3.

✗ Brittle — counts rows
// "Remove Top Rows → 4"
Table.Skip(Source, 4)

Breaks the moment the preamble changes height.

✓ Resilient — finds an anchor
// Skip rows until one of them contains "Order ID"
Table.Skip(Source, each not List.Contains(
    List.Transform(Record.FieldValues(_),
                   (v) => Text.Trim(Text.From(v))),
    "Order ID"))

Works whether the preamble is 2 rows or 12.

Reading that snippet: Table.Skip normally takes a number, but it also accepts a condition — "keep skipping while this is true". Record.FieldValues(_) is the current row as a list of values; List.Transform turns each value into trimmed text so the comparison is reliable; List.Contains asks "is the anchor word anywhere in this row?". Then Home → Use First Row as Headers.

Pick an anchor that cannot be renamed — an ID column, usually. And know the failure mode: if the anchor is never found, Table.Skip skips everything and you get an empty table rather than an error. The change detector catches that; a row-count check catches it too.

Problem 2: the header looks identical but isn't

"Sales " with a trailing space, "Net#(lf)Sales" with a line break from a wrapped cell, or a non-breaking space pasted out of a web report. You cannot see any of it, and every rename and column reference fails. Normalise the names before you try to match them.

// Clean every column name in one step, whatever it's called
Table.TransformColumnNames(Source, each
    Text.Trim(
      Text.Clean(                            // strips control chars
        Text.Replace(
          Text.Replace(_, "#(lf)", " "),    // line feeds → space
          Character.FromNumber(160), " "))))  // nbsp → space
The same trick for values, not just headers

Non-breaking spaces hide in data too, and they are why a lookup "obviously" matches but returns nothing. Text.Clean alone won't remove them — character 160 is not a control character. Add the Character.FromNumber(160) replace to your text-cleanup step as a matter of routine.

Problem 3: the auto "Changed Type" step

Power Query adds a Changed Type step immediately after Source, naming every single column. It is the most common cause of a broken monthly refresh: drop one column from the source and the query fails at step 2 with an error that points at the wrong place.

Delete it

Remove the automatic Changed Type step. Set types deliberately at the end, once you have pinned the schema and know exactly which columns exist.

Stop it happening

File → Options and settings → Query Options → Data Load, and untick Automatically detect column types and headers for unstructured sources.

🧹 Junk rows: totals, blanks and footnotes

The rows above your data are a header problem. The rows inside and below it are worse, because they look like data. A subtotal row lands in your SUMIFS. A "* excludes intercompany" footnote breaks your date conversion. And neither appears every month.

One filter handles all three

Junk rows share a tell: the key column is either empty or isn't a real key. Filter on that, not on row position.

// Keep only rows that look like genuine records
Table.SelectRows(Source, each
       [Order ID] <> null
   and [Order ID] <> ""
   and not Text.StartsWith(Text.From([Order ID]), "Total")
   and not Text.StartsWith(Text.From([Order ID]), "Subtotal")
   and not Text.StartsWith(Text.From([Order ID]), "*"))

M's and short-circuits left to right, so the null check protects the Text.StartsWith calls that follow it. Keep the null test first.

Even better: match the shape

If real IDs always look like XX-0000-000000, test for that instead of blacklisting words. It survives a subtotal row labelled in French.

// Keep rows whose ID starts with 2 letters + "-"
Table.SelectRows(Source, each
    Text.Length(Text.From([Order ID])) > 3
    and Text.At(Text.From([Order ID]), 2) = "-")

Blank rows, properly

Home → Remove Rows → Remove Blank Rows drops rows where every cell is empty. This is the M it writes — worth recognising:

Table.SelectRows(Source, each not List.IsEmpty(
    List.RemoveMatchingItems(
        Record.FieldValues(_), {"", null})))

Note it will not remove a subtotal row — that row has values.

Order of operations for merged-cell exports

Exports with merged cells arrive with a value on the first row of each block and null underneath. Transform → Fill → Down repairs it — but only if you do it before you remove blank rows or filter anything out. Fill down first, filter second. Get that backwards and you fill values into the wrong groups without any warning.

Cut the tail off, safely

Never use Remove Bottom Rows → 3 to lose the totals block. The block is 3 rows this month and 5 next month, and the step will happily eat real data. Filter on content, always.

🔢 Types: numbers as text, dates in the wrong language

Typing is where a "mostly the same" file does its real damage, because a type error stops the whole query while a successful mis-conversion doesn't.

Rule 1: type last, and only what you pinned

Table.TransformColumnTypes has no MissingField option — name a column that isn't there and it fails. That's fine, because by the time you type, the schema is pinned and every column is guaranteed to exist. This is the whole reason typing goes at the end.

// Safe: these columns exist because SelectColumns guaranteed them
Table.TransformColumnTypes(Pinned, {
    {"Order ID",    type text},
    {"Order Date",  type date},
    {"Region",      type text},
    {"Sales",       type number}
}, "en-GB")                    // ← the locale argument. Never omit it.

Rule 2: always pass a locale for dates

Without a locale

Excel uses the machine's regional settings. 03/04/2026 is 3 April on your laptop and 4 March on your colleague's. Both refresh green. Only one is right.

→
With a locale

The same file gives the same answer on every machine, forever. Use the ribbon: Transform → Data Type → Using Locale…, or type the culture code as the third argument.

Common culture codes: "en-GB" day/month/year · "en-US" month/day/year · "de-DE" comma decimals · "fr-FR" · "en-AU".

The tell-tale symptom

If a date column converts fine for most rows and errors on a few, you almost certainly have the locale backwards: 13/04 can't be a month so it errors, while 03/04 silently becomes the wrong day. A handful of date errors means all your dates are suspect, not just the failing ones.

Rule 3: convert numbers tolerantly

Currency symbols, thousands separators, a stray - for nil, accounting negatives in brackets, a percentage sign. Table.TransformColumns lets you write the conversion yourself, and it does take a MissingField argument.

// Strip the decoration, then convert. Anything hopeless → null.
Table.TransformColumns(Source, {
    {"Sales", each try Number.From(Text.Remove(Text.From(_),
                  {"$", "£", "€", ",", " "}))
                  otherwise null, type number},
    {"Discount", each try Number.From(_) otherwise null, type number}
}, null, MissingField.Ignore)
Handling accounting negatives — (1,234.00) means −1234 
// Full-strength number cleaner: brackets, symbols, blanks and dashes
each
  let
      t = Text.Trim(Text.From(_)),
      isNeg = t <> null and Text.StartsWith(t, "(")
                        and Text.EndsWith(t, ")"),
      core  = if isNeg then Text.Middle(t, 1, Text.Length(t) - 2) else t,
      bare  = Text.Remove(core, {"$", "£", "€", ",", " ", "%"}),
      num   = if bare = null or bare = "" or bare = "-"
              then null
              else try Number.From(bare) otherwise null
  in
      if isNeg and num <> null then -num else num

Drop that into Add Column → Custom Column, or use it as the transformation inside Table.TransformColumns. It covers essentially every finance export you'll meet.

try … otherwise null is a loaded gun

It converts loud failures into quiet blanks. That's exactly what you want for a report that must not stop — and exactly what you don't want if you never look at the blanks. Pair it with a null count in your change detector, or route the failures to a rejects table. "Zero errors" and "zero problems" are not the same statement.

Dates arriving as text in one known format 
// Explicit format + culture beats guessing
Table.TransformColumns(Source, {
    {"Order Date", each try Date.FromText(Text.Trim(Text.From(_)),
        [Format = "dd/MM/yyyy", Culture = "en-GB"])
        otherwise null, type date}
}, null, MissingField.Ignore)
A date column that is half real dates, half Excel serial numbers 
// 45689 is a serial number; "03/04/2026" is text. Handle both.
each if _ = null then null
     else if Value.Is(_, type number) then Date.From(_)
     else try Date.FromText(Text.Trim(Text.From(_)),
              [Format = "dd/MM/yyyy", Culture = "en-GB"]) otherwise null

This happens whenever somebody has typed a few rows by hand into an otherwise-clean export.

Text columns: normalise the values, not just the type

West, west and WEST are three regions as far as a Group By is concerned. Standardise as part of typing: Text.Proper(Text.Trim(Text.From(_))). Do it in the Clean query so every downstream query benefits.

🕳️ The silent killer: filters that freeze a list

This one costs people their credibility, because there is no error, no warning, and no clue in the Applied Steps. It looks exactly like a working query.

You open the ▾ dropdown on Region, untick Internal, click OK. Power Query does not record "everything except Internal". It records the list of values you left ticked — a snapshot of the regions that existed on the day you built it:

// What the checkbox dialog actually wrote
Table.SelectRows(Source, each List.Contains(
    {"East", "West", "Central", "South"}, [Region]))

In June the business opens a North region. North isn't on the list. Every North row is dropped. Your total is short by an entire region, the query refreshes without complaint, and you present it.

✗ Include list — closed to the future
Table.SelectRows(Source, each List.Contains(
    {"East","West","Central","South"}, [Region]))

New values are excluded by default. Silently.

✓ Exclude list — open to the future
Table.SelectRows(Source, each not List.Contains(
    {"Internal", "Test"}, [Region]))

New values are included by default. Which is what you meant.

The rule: state what you're removing, never what you're keeping

Whenever the set of values can grow — regions, categories, product lines, cost centres, sales reps, statuses — write the filter as an exclusion. Use the dropdown's Text Filters → Does Not Equal rather than the checkboxes, or just edit the formula bar. Reserve include-lists for sets that genuinely cannot change, like {"Yes","No"}.

Dates: relative, not absolute

"Order Date is after 01/01/2026" needs editing every year. Write it against today instead, so it moves on its own:

// Rolling 13 months, no maintenance
Table.SelectRows(Source, each [Order Date] >=
    Date.AddMonths(Date.StartOfMonth(
        DateTime.Date(DateTime.LocalNow())), -12))

Or drive it from a parameter

When the reporting period is a business decision rather than a rolling window, make it a parameter (pStartDate) and change it in one dialog — not by hunting through steps.

Table.SelectRows(Source,
    each [Order Date] >= pStartDate)
Audit the filters you already have

Open every existing query, click each Filtered Rows step, and read the formula bar. Any List.Contains({…}, [SomeColumn]) on a growable column is a bug waiting for the right month. This is a ten-minute job that has saved more reports than any other item in this lesson.

📂 Sources that move: paths, sheets and folders

Never hard-code a path

A step that says C:\Users\dave\Downloads\Sales_Feb.xlsx is broken for every colleague and broken next month. Put it in a parameter: Home → Manage Parameters → New Parameter, type Text.

// pFolder = "C:\Finance\Monthly\"   (a Text parameter)
// pFile   = "Sales_2026_02.xlsx"    (a Text parameter)
Source = Excel.Workbook(File.Contents(pFolder & pFile), null, true)

Better still, put the path in a cell on a worksheet, make it a one-cell named Table, and read it with Excel.CurrentWorkbook(). Then whoever runs the report can repoint it without ever opening the Power Query editor.

The sheet gets renamed every month

Feb 2026, then Mar 2026. Power Query recorded the exact name and now can't find it: The key didn't match any rows in the table. Select the sheet by pattern or by position instead.

// By pattern — the safest, if the name has a stable word in it
Sheet = Table.SelectRows(Source,
            each [Kind] = "Sheet"
             and Text.Contains(Text.Lower([Name]), "detail")){0}[Data]

// By position — first worksheet, whatever it's called
Sheet = Table.SelectRows(Source, each [Kind] = "Sheet"){0}[Data]

// Best of all — if the source has a real Excel Table, use it by name
Sheet = Source{[Item = "tblSales", Kind = "Table"]}[Data]

Excel.Workbook() returns one row per sheet, named range and Table, with a Kind column telling you which is which. Filtering on Kind = "Sheet" stops a stray named range being picked up. A real Excel Table in the source is always the most stable target — if you can persuade whoever sends the file to add one, do.

A folder of files that aren't quite identical

From Folder plus Combine & Transform builds a helper query from one sample file. That's perfect when all the files match, and fragile when they don't — one odd file kills the whole combine. When the files vary, write your own cleaning function and apply it per file.

  1. Filter the file list before you read anything

    Folders collect junk: Excel's ~$ lock files, an archive subfolder, someone's .pdf.

    Files = Table.SelectRows(Source, each
        not Text.StartsWith([Name], "~$")
    and Text.EndsWith(Text.Lower([Name]), ".xlsx")
    and not [Attributes][Hidden])
  2. Write a cleaning function as its own query

    New Query → Blank Query → Advanced Editor. It takes one raw table and returns a table with a guaranteed shape — every defensive trick from this lesson lives in here, once.

    // Query name: fnClean
(Raw as table) as table =>
let
    Promoted = Table.PromoteHeaders(Raw, [PromoteAllScalars = true]),
    Tidy     = Table.TransformColumnNames(Promoted,
                   each Text.Trim(Text.Clean(_))),
    Named    = Table.RenameColumns(Tidy,
                   {{"Net Sales", "Sales"}}, MissingField.Ignore),
    Pinned   = Table.SelectColumns(Named,
                   {"Order ID", "Order Date", "Region", "Sales"},
                   MissingField.UseNull)
in
    Pinned
  3. Apply it to every file, keeping failures visible

    Wrapping the call in try means one broken file can't stop the other eleven — but you still get told which one it was.

    Called = Table.AddColumn(Files, "Result", each try fnClean(
             Table.SelectRows(Excel.Workbook([Content]),
                 each [Kind] = "Sheet"){0}[Data])),

Good   = Table.SelectRows(Called, each not [Result][HasError]),
Bad    = Table.SelectRows(Called, each [Result][HasError])
  4. Expand the good ones, and load the bad ones too

    Because every file went through fnClean, they all have the same columns and stack perfectly.

    Data = Table.AddColumn(Good, "Table", each [Result][Value]),
Out  = Table.ExpandTableColumn(
           Table.SelectColumns(Data, {"Name", "Table"}), "Table",
           {"Order ID", "Order Date", "Region", "Sales"})
Keep the file name

The Name column is often the only record of which month a row belongs to, and it's your first debugging tool: group by it and count rows. A file with 3 rows where the others have 4,000 is a failed export, not a quiet month.

Load Bad to a sheet

Add a column with each [Result][Error][Message] and load it. Two lines of work gives you a "files that failed this month, and why" report that appears automatically every refresh.

⚠️ Route your errors, don't delete them

When a value won't convert, Power Query puts an Error in that cell. The ribbon offers Remove Errors, and it is the most over-used button in the product: it makes the red go away and takes the evidence with it.

Remove Errors

Table.RemoveRowsWithErrors. Deletes the row entirely. Your totals drop and nothing tells you by how much.

Replace Errors

Table.ReplaceErrorValues. Keeps the row, swaps the bad cell for null or 0. Safer — the row still counts.

Keep Errors ⭐

Table.SelectRowsWithErrors. On a referenced query, this becomes your rejects report.

The rejects pattern

Reference the query before its error handling, twice. One branch is your clean output; the other is everything that failed. Both refresh together, so a problem can never hide.

An empty rejects table is a good month

Put it on a sheet next to your output with a row count above it. Zero rows means the file was clean; forty rows means go and look. Either way you know, which is the entire difference between a report you can defend and one you can't.

Errors versus nulls — not the same thing

An Error is "this failed to convert". A null is "there was nothing here". Once you write try … otherwise null the distinction is gone forever, so decide deliberately: use try/otherwise where blank is genuinely acceptable, and let the error stand where it isn't.

🐤 The change detector

Everything so far makes the query survive a changed file. This makes it tell you the file changed — which matters, because "survived" sometimes means "quietly produced nulls all month".

Build one small query that compares this month's reality against your expectations and loads to a corner of a sheet. Read it for five seconds after every refresh.

// Query name: Check_Schema — load this one to a sheet
let
    Expected  = {"Order ID", "Order Date", "Customer ID",
                 "Region", "Sales", "Discount"},
    Actual    = Table.ColumnNames(Raw_Sales),
    Missing   = List.Difference(Expected, Actual),
    Extra     = List.Difference(Actual, Expected),

    Rows      = Table.RowCount(Clean_Sales),
    NullSales = List.Count(List.Select(
                    Table.Column(Clean_Sales, "Sales"), each _ = null)),
    NullDates = List.Count(List.Select(
                    Table.Column(Clean_Sales, "Order Date"), each _ = null)),

    Report = #table(
        type table [Check = text, Detail = text, Status = text],
        {
          {"Columns expected but missing", Text.Combine(Missing, ", "),
              if List.IsEmpty(Missing)  then "OK" else "⚠ LOOK"},
          {"Columns new this month",     Text.Combine(Extra, ", "),
              if List.IsEmpty(Extra)    then "OK" else "⚠ LOOK"},
          {"Rows loaded",                Text.From(Rows),
              if Rows > 0              then "OK" else "✗ FAIL"},
          {"Sales blank",                Text.From(NullSales),
              if NullSales = 0         then "OK" else "⚠ LOOK"},
          {"Order Date blank",           Text.From(NullDates),
              if NullDates = 0         then "OK" else "⚠ LOOK"}
        })
in
    Report

Two more checks worth adding

Row count per month

Group the combined data by source file or month and count. A month that is 10× or 0.1× its neighbours is a broken export, and the pattern is obvious at a glance.

Reconcile to the source total

If the export prints a grand total, capture it and compare against List.Sum of your loaded column. Matching to the penny is the strongest evidence you have that nothing was dropped.

Make failure impossible to ignore

Put the Checks table at the top of the sheet people actually open, and add conditional formatting so anything other than OK turns red. A check nobody sees is a check that doesn't exist.

📜 The whole thing, in one script

This is the Clean_Sales query from the four-query architecture, with every technique in this lesson applied in the right order. Paste it into View → Advanced Editor, change the column names to yours, and you have a query that will survive most of what next month throws at it.

let
    // 1 ─ Source. The path lives in a parameter, never in a step.
    Source  = Excel.Workbook(File.Contents(pFolder & pFile), null, true),

    // 2 ─ Pick the sheet by pattern, not by its exact (monthly) name.
    Sheet   = Table.SelectRows(Source, each [Kind] = "Sheet"
                  and Text.Contains(Text.Lower([Name]), "detail")){0}[Data],

    // 3 ─ Drop the title block: skip rows until one holds the anchor.
    Skipped = Table.Skip(Sheet, each not List.Contains(
                  List.Transform(Record.FieldValues(_),
                      (v) => Text.Trim(Text.From(v))), "Order ID")),
    Headers = Table.PromoteHeaders(Skipped, [PromoteAllScalars = true]),

    // 4 ─ Normalise header text so matching is reliable.
    Tidy    = Table.TransformColumnNames(Headers, each Text.Trim(
                  Text.Clean(Text.Replace(
                      Text.Replace(_, "#(lf)", " "),
                      Character.FromNumber(160), " ")))),

    // 5 ─ Accept every alias the source has ever used for a column.
    Named   = Table.RenameColumns(Tidy, {
                  {"Cust ID",      "Customer ID"},
                  {"Customer Id",  "Customer ID"},
                  {"Net Sales",    "Sales"},
                  {"Sales Amount", "Sales"},
                  {"Rgn",          "Region"}
              }, MissingField.Ignore),

    // 6 ─ Pin the schema. Missing → null. New → ignored. Order → mine.
    Pinned  = Table.SelectColumns(Named,
                  {"Order ID", "Order Date", "Customer ID",
                   "Region", "Sales", "Discount"},
                  MissingField.UseNull),

    // 7 ─ Remove totals, footnotes and blanks by content, not position.
    Real    = Table.SelectRows(Pinned, each
                     [Order ID] <> null
                 and [Order ID] <> ""
                 and not Text.StartsWith(Text.From([Order ID]), "Total")
                 and not Text.StartsWith(Text.From([Order ID]), "Subtotal")
                 and not Text.StartsWith(Text.From([Order ID]), "*")),

    // 8 ─ Clean the values: text tidied, money stripped of decoration.
    Values  = Table.TransformColumns(Real, {
                  {"Region", each Text.Proper(Text.Trim(Text.From(_))),
                      type text},
                  {"Sales", each try Number.From(Text.Remove(Text.From(_),
                      {"$", "£", "€", ",", " "})) otherwise null,
                      type number},
                  {"Discount", each try Number.From(_) otherwise null,
                      type number}
              }, null, MissingField.Ignore),

    // 9 ─ Type it last, with an explicit locale. Safe: schema is pinned.
    Typed   = Table.TransformColumnTypes(Values, {
                  {"Order ID",    type text},
                  {"Order Date",  type date},
                  {"Customer ID", type text}
              }, "en-GB")
in
    Typed
Why this order and no other

Find the headers before you can name columns → normalise the names before you can match them → alias them before you can pin them → pin the schema before you can safely type → filter junk rows before typing, so a footnote can't create errors → type last, when every column is guaranteed to exist. Each step depends on the one above it. Shuffle them and you reintroduce exactly the fragility you removed.

Steps 5, 6, 7 and 9 are the four lines you will edit when the source changes — and they are the only ones. That is what the architecture buys you: a known place to look.

🔧 Troubleshooting: message → cause → fix

What Power Query saysWhat actually happenedWhat to do
The column 'X' of the table wasn't found Renamed or dropped in the source — very often at the auto Changed Type step Add an alias, then pin with MissingField.UseNull. Delete the auto Changed Type step.
The key didn't match any rows in the table The sheet, Table or named range you navigated to has been renamed Select the sheet by pattern or position instead of by exact name.
We couldn't find the file… / DataSource.Error Hard-coded path; file moved, renamed, or is on someone else's Downloads folder Move the path into a parameter or a worksheet cell.
DataFormat.Error: We couldn't convert to Number Text in a numeric column — currency symbol, n/a, a footnote row, or a thousands separator Filter junk rows first, then convert tolerantly with try … otherwise null.
Headers show as Column1, Column2… The title block changed height, so Promote Headers grabbed the wrong row Anchor the header row on a word that's always in it.
Query returns zero rows, no error The header anchor wasn't found (so everything got skipped), or a filter excluded everything Click back through the Applied Steps and find the step where the rows disappeared. Add a row count to your checks.
Totals are lower than expected, no error A frozen include-list filter dropped a new category, or Remove Errors deleted rows Invert the filter to an exclusion; swap Remove Errors for a rejects query.
Totals are higher than expected, no error A subtotal or grand-total row is being counted as data Filter junk rows on the key column.
Dates are wrong by a few days, or a few error Locale mismatch — day/month read the wrong way round Retype with Using Locale… and an explicit culture. Treat every date as suspect, not just the failures.
A column exists but is all null Appended tables whose column names differ (Order Date vs OrderDate), or MissingField.UseNull doing its job Standardise names before appending. If it's UseNull, your check query already told you which column vanished.
Formula.Firewall: … references other queries or steps Privacy levels: one query combines a workbook table (your alias map) with an external file Query Options → Privacy → Ignore the Privacy Levels for this file, or read both sources inside a single query.
Refresh has become very slow Intermediate queries loading to sheets, or filters applied after expensive steps Set helpers to Connection Only, filter and remove columns as early as possible.
How to debug any of them in 60 seconds

Click each Applied Step from the top and watch the row count in the status bar. The step where the count goes wrong is your bug — you don't need to read a single line of M to find it.

📋 The five-minute monthly run

Once the query is built properly, the monthly process is a checklist rather than a project. Work down it in order and stop at the first thing that looks wrong.

  • Drop the new file in the folder — or update pFile if you're pointing at one file
  • Data → Refresh All (Ctrl Alt F5) and let it finish
  • Read the Checks table: any missing columns, any new columns?
  • Check the row count against last month — same order of magnitude?
  • Check the rejects table is empty (or that you understand why it isn't)
  • Reconcile one number — a grand total — against the source file
  • Spot-check three rows end to end: source file → output table → final figure
  • Only then look at the actual analysis
When something has changed

Fix it in Clean_, not in the output query and never on the worksheet. Add the alias, add the exclusion, widen the type handling. Then write one line in a notes sheet: "Mar 2026 — Discount renamed to Discount %, alias added." In eighteen months that note is the only reason anyone can explain a break in the trend.

Never patch the output by hand

Typing a corrected value into the loaded table is erased by the next refresh — and until then, your workbook disagrees with its own query. If a value is wrong, it is wrong in the source or in a step. Fix it there.

🧠 The habits, condensed

  • Declare what you want, don't remove what you don't — Table.SelectColumns(…, MissingField.UseNull) is the single highest-value line in this lesson
  • Never count rows or columns — anchor on content that can't move
  • Normalise names before matching them — trailing spaces and line breaks are invisible and fatal
  • Keep an alias list, on a worksheet once it grows past a handful
  • Filter by exclusion, so new categories arrive instead of vanishing
  • Type last, with a locale, after the schema is guaranteed
  • Route errors to a rejects table rather than deleting them
  • Ship a change detector — surviving silently is not the same as being correct
  • Split into Raw → Clean → Output, so there is one place to fix things
  • Rename every step in plain English
  • Parameterise every path, and every date boundary you'd otherwise retype
The mindset

Write every step as an answer to "what if this is slightly different next month?". You are not automating this file; you are describing the family of files it belongs to. Ten extra minutes now buys you back a morning of panic every quarter — and, more valuable than the time, a report you can actually vouch for.

🎯 Practice exercises

Desktop Excel required. Take any dataset, save it as Report_Jan.xlsx, and build the query. Then sabotage a copy called Report_Feb.xlsx and see what survives.

Build it

  1. Create the four-query structure: pFolder and pFile parameters, Raw_Sales, Clean_Sales, Sales — with only the last one loaded to a sheet
  2. In Clean_Sales, delete the automatic Changed Type step
  3. Pin the schema with Table.SelectColumns(…, MissingField.UseNull), listing six columns
  4. Add a Table.RenameColumns(…, MissingField.Ignore) alias step before it
  5. Type the columns at the very end, passing an explicit locale
  6. Rename every step so the list reads as plain English
  7. Build Check_Schema and load it to a "Checks" sheet

Break it

In Report_Feb.xlsx, make one change at a time, point pFile at it, refresh, and write down what happened before you fix it.

  1. Rename Sales to Net Sales — does the Checks table catch it?
  2. Delete the Discount column entirely — does the output keep its shape?
  3. Add a Notes column — does it leak into your output?
  4. Reorder three columns — does anything change at all? (It shouldn't.)
  5. Insert two extra rows above the headers — fix it with an anchor rather than a count
  6. Add a Grand Total row at the bottom — does your total double?
  7. Put £1,234.50 in one Sales cell — make it convert instead of erroring
  8. Type n/a in another — send it to a rejects table rather than deleting the row
  9. Add a new region called North — if your rows drop, you have a frozen filter to invert
  10. Add a trailing space to the Region header — fix it with Table.TransformColumnNames
🏆 Challenge: the folder that fights back

Build a folder pipeline over twelve monthly files using your own fnClean function rather than the auto-generated sample-file helper. Then corrupt one file — delete its header row entirely. A good pipeline loads the other eleven, lists the failed file and its error message on a sheet, and reports the row count per month so the gap is obvious. Get that working and you have built something genuinely production-grade.
