📐 Table Calculations

Running totals, percent of total, rank, moving averages, year-over-year growth. Table calculations work on the numbers already in your view rather than the underlying rows. That single difference explains both what they can do — anything positional, like "compared to the row above" — and what they can't: see data your filters removed.

📖 Terms on this page

Defined before they're used. Every term on the site is also in the glossary.

Table calculation
A calculation that runs on the numbers already in your view, not on the source data.
Example: Running total, rank, percent of total, year-over-year growth.
📍 Right-click a measure pill → Quick Table Calculation
Compute Using / addressing
The direction the calculation travels through your table.
Example: Percent of Total computed across makes each row total 100%; down makes each column total 100%.
Partition
The group the calculation restarts within.
Example: A running total that resets each January is partitioned by Year.
Window
The set of cells the calculation can see, set by Compute Using.
Example: WINDOW_AVG averages across that set.
The △ marker
A small triangle Tableau adds to a pill carrying a table calculation.
Example: If a number looks wrong, check for this first — it changes what the pill means.
LOOKUP
A function fetching a value from another position in the table.
Example: LOOKUP(SUM([Sales]), -1) is "the previous period's value".

A table calc cannot see rows your filters removed

A table calculation cannot see rows that aren't in your view. Filter out the South region and a "percent of total" calculation now totals only Central, East and West — the percentages change. That's not a bug; it's the definition. It's also the single most common source of confusion, and the reason LOD expressions exist.

🧭 Compute Using — the part everyone gets wrong

A table calculation needs to know which direction to move through the table. Get this wrong and you'll get a plausible-looking number that answers a different question.

Right-click the pill → Compute Using, or Edit Table Calculation for full control.

Table (across)

Moves left → right along each row, restarting on every new row. Use for "% of this row's total".

Table (down)

Moves top → bottom down each column, restarting on every new column.

Table (across then down)

Treats the entire table as one continuous sequence. Use for "% of the grand total".

Pane (down)

Restarts at each pane boundary — e.g. per year rather than across the whole table.

✓ Specific Dimensions

Tick exactly which dimensions the calculation walks along. Explicit, survives rearranging the view, and the option you should reach for once you understand it.

⚠️ Cell

Each cell on its own. Almost never useful — if you land here by accident, your numbers will all be 100% or 1.

What "direction" actually means

The calculation walks through the cells of your table in a path. Compute Using sets that path — and the arrows below are literally it.

How to check you got it right

Ask what should add up to 100% — rows, columns, or the whole table — then verify that it actually does. If nothing sums to 100%, your Compute Using is wrong. This takes five seconds and catches almost every mistake.

🧷 Addressing vs partitioning — what Compute Using really sets

"Table (across)" and "Pane (down)" are shorthand. Underneath, every table calculation splits the dimensions in your view into two piles, and those two piles are the entire configuration. Choose Specific Dimensions in the dialog and you're setting them by hand — which is why that option is the one worth learning.

☑ Ticked — addressing

The dimensions the calculation moves along. These define the direction of travel and the order of the cells it walks through.

Tick Month and a running total accumulates month by month.

☐ Unticked — partitioning

The dimensions the calculation restarts for. Each combination of these gets its own independent window.

Leave Region unticked and each region gets its own running total from zero.

The sentence that makes it click

Ticked dimensions are what the calculation walks along. Unticked dimensions are what it starts over for. Every dimension in the view is in exactly one of the two piles — there is no third option, and Tableau puts every dimension somewhere whether you thought about it or not.

This is what "Table" and "Pane" are choosing for you. Table addresses everything; Pane partitions by whatever creates the panes. Naming the dimensions yourself removes the guesswork.

How the presets map onto the two piles

Table (down)Every dimension on RowsEvery dimension on Columns
Table (across then down)EverythingNothing — one window for the whole table

Why the presets break when you rearrange the view

"Table (across)" doesn't mean "along the months". It means "along whatever is on Columns". Move the date pill to Rows — or add a second dimension beside it — and the calculation silently starts walking a different path. The numbers stay plausible and the chart still draws, which is what makes it dangerous.

Specific Dimensions names the fields, so the calculation means the same thing however you rearrange the sheet. Once a workbook is going to be published, convert every table calc to Specific Dimensions.

Nested table calcs and the Calculation dropdown

Once a secondary calculation exists, the top of the dialog grows a Calculation dropdown listing both stages. Each stage has its own Compute Using — they are not required to match, and often shouldn't. A Pareto chart, for instance, accumulates along sub-categories and then takes a percentage of that same window; a year-on-year index accumulates along months but rebases per year.

If a two-stage calculation gives a nonsense answer, check both stages. People almost always set the first and forget the second exists.

➗ Percent of what? — choosing the denominator

Percent of Total is the calculation people reach for first and get wrong most often, and the reason is that "percent" is only half a question. Every ratio is "X out of Y", and Tableau can work out the numerator without your help. Y is the entire decision — and nothing on the finished chart records which Y you picked.

Same four numbers, same formula, three different questions. Two of these are wrong for whatever you are actually asking — and the chart looks equally convincing in all three cases.

The rule, in one line

In Specific Dimensions: a ticked dimension is swept into the denominator. An unticked dimension is your "within".

"Percent within Education" therefore means tick Gender, untick Education — add up across the genders, hold the education fixed. It is the same addressing-versus-partitioning switch as the section above; here the partition is the denominator.

Why this is really conditional proportion

What makes percentages confusing isn't Tableau — it's that the word "percentage" quietly hides a second variable. Written out, the three answers above are three different conditional proportions:

QuestionIn symbolsLeft unticked — the "given"
Share of everyoneP(Bachelor's and Male)nothing
Of the Bachelor's, share maleP(Male | Bachelor's)Education
Of the males, share Bachelor'sP(Bachelor's | Male)Gender

The bar in P(A | B) reads as "given", and the definition is P(A and B) ÷ P(B) — so whatever sits after the bar is the denominator. That is exactly the field you leave unticked. Note too that the last two rows are not interchangeable: 57.1% and 80% are both true statements about the same 400 people, and swapping one for the other is a real analytical error rather than a rounding difference.

Say it out loud before you build it

Phrase the number as "X out of Y" and name Y explicitly. "Male out of Bachelor's graduates." "Bachelor's out of males." "Bachelor's out of everyone." Once Y has a name the setup is mechanical: Y is what you leave unticked, and Y is what must sum to 100%.

Then check it — add up a row, add up a column. Whichever direction you meant should come to exactly 100%. If nothing does, the Compute Using is wrong. Five seconds, and it catches almost every mistake in this section.

Changing the function does not change the denominator
// Equivalent within a partition — swapping one for
// the other fixes nothing.
COUNT([Education]) / TOTAL(COUNT([Education]))
COUNT([Education]) / WINDOW_SUM(COUNT([Education]))

TOTAL and WINDOW_SUM both operate over the current partition, so with the same Compute Using they return the same number. When a percentage is measured against the wrong group the formula is not the problem — the partitioning is. Open Edit Table Calculation and change what's ticked.

The same goes for the Quick Table Calculation. Percent of Total has to guess a direction from your layout, so treat it as a starting point and set the dimensions explicitly afterwards.

When the denominator isn't in the view — or shouldn't move

A table calculation can only divide by numbers that are on screen. Two cases break that, and both are jobs for an LOD expression:

  • The denominator is at a grain you aren't showing. "Each sub-category as a share of its region" in a view with no Region on it — SUM([Sales]) / MIN({FIXED [Region] : SUM([Sales])}).
  • The denominator must survive filtering. A table calc's percentages re-scale to sum to 100% across whatever the viewer left; {FIXED : SUM([Sales])} keeps measuring against the whole company. Which is right depends on whether you mean "share of the selection" or "share of the business" — and it's worth saying which in the title.

LOOKUP — reaching to another row

Every “compared to last period” calculation is really a LOOKUP with a negative offset.

Year-over-year growth in four clicks

  1. Build the base view

    YEAR(Order Date) on Columns, SUM(Sales) on Rows.

  2. Add the calculation

    Right-click SUM(Sales) → Quick Table Calculation → Percent Difference.

  3. Check the direction

    Compute Using should be Table (across) — along the years. 2014 will be blank, because there's no prior year to compare to. That blank is correct.

  4. Format it

    Right-click the axis → Format → Percentage, 1 decimal. You now have a growth-rate view that updates with any filter.

Show the moving average and the raw line together

Daily or monthly sales are noisy enough that trends are hard to see. A 3-month moving average on top of the raw line shows the underlying direction while keeping the actual values visible. Add both to the view and make the moving average a thicker, darker line.

✍️ Writing them by hand

Quick Table Calcs cover most cases. When you need more control, write the function directly.

// Running total of sales
RUNNING_SUM(SUM([Sales]))

// Percent of total
SUM([Sales]) / TOTAL(SUM([Sales]))

// Rank — descending by default
RANK(SUM([Sales]))
RANK_DENSE(SUM([Sales]))      // ties share a rank, no gaps
RANK_UNIQUE(SUM([Sales]))     // ties broken arbitrarily

// Difference from the previous period
ZN(SUM([Sales])) - LOOKUP(ZN(SUM([Sales])), -1)

// Percent difference (year-over-year growth)
(SUM([Sales]) - LOOKUP(SUM([Sales]), -1))
    / LOOKUP(SUM([Sales]), -1)

// 3-period moving average (2 back, 0 forward)
WINDOW_AVG(SUM([Sales]), -2, 0)

// Share of the window's maximum — useful for index charts
SUM([Sales]) / WINDOW_MAX(SUM([Sales]))
Table calcs always wrap an aggregate

RUNNING_SUM([Sales]) is invalid — it must be RUNNING_SUM(SUM([Sales])). The inner aggregate produces the view's numbers; the table calc then walks over them. If Tableau complains about mixing aggregate and non-aggregate arguments, this is nearly always why.

LOOKUP — the time-travel function

LOOKUP(expression, offset) fetches a value from another position in the table. It's the engine behind every "compared to last period" calculation.

ExpressionReturns
LOOKUP(SUM([Sales]), -1)The previous period's value
LOOKUP(SUM([Sales]), 1)The next period's value
LOOKUP(SUM([Sales]), -12)Twelve periods back — same month last year
LOOKUP(SUM([Sales]), FIRST())The first value in the window — the base for an index
LOOKUP(SUM([Sales]), LAST())The last value in the window

Offsets that fall outside the window return Null, which is why the first period of a year-over-year view is always blank. Wrap in ZN() only if you genuinely want zero — a blank is usually the more honest answer.

🪟 WINDOW functions and partitioning

Every table calculation operates over a window — the set of cells it can see. Compute Using defines that window, and the WINDOW_* family lets you aggregate across it.

WINDOW_SUM(SUM([Sales]))        // total across the window
WINDOW_AVG(SUM([Sales]))        // average across the window
WINDOW_MAX(SUM([Sales]))        // biggest in the window
WINDOW_MIN(SUM([Sales]))
WINDOW_MEDIAN(SUM([Sales]))
WINDOW_STDEV(SUM([Sales]))

// Optional start/end offsets narrow the window
WINDOW_AVG(SUM([Sales]), -2, 0)   // this period + 2 before
WINDOW_SUM(SUM([Sales]), FIRST(), 0)  // same as RUNNING_SUM

// Positional helpers
INDEX()    // position in the window: 1, 2, 3…
SIZE()     // how many rows are in the window
FIRST()    // offset to the first row (0 when you're on it)
LAST()     // offset to the last row
INDEX() as a Top N filter that respects other filters

Put INDEX() <= 10 on the Filters shelf with the view sorted descending. Unlike a Top N filter, this one is applied after other filters — so "top 10 within whatever the user selected" works without touching context filters. It's the standard fix for dashboards where the Top N should respond to a filter card.

🕰️ Late filters — filtering after the calculation

A filter placed on a table calculation runs at the very end of the pipeline, after the calculation has already been computed. That sounds like a footnote and it is actually one of the most useful things table calcs can do: it lets you hide marks without changing the answer.

An ordinary filter
Filter: YEAR(Order Date) = 2015, 2016, 2017

2014 is gone before the calculation runs, so 2015's year-over-year growth has nothing to compare against and comes out blank. You removed one year and lost two.

→
A late filter
Filter on a table calc:
  LOOKUP(MIN(YEAR([Order Date])), 0) >= 2015

2014 is present while the growth is computed, then hidden. 2015 keeps its number and the chart starts where you wanted.

The LOOKUP(…, 0) trick

Wrapping anything in LOOKUP(expression, 0) fetches the value at offset zero — the current row. It changes nothing about the value; what it changes is when the expression is evaluated, because a LOOKUP is a table calculation and therefore runs last. It is the standard way to turn any ordinary condition into a late filter.

The same reasoning explains INDEX() <= 10 as a Top N that respects the user's filter cards — see Filters.

Late filters hide, they don't remove

The rows are still in the query, still in the grand totals, still in every other table calculation's window. That's exactly what you asked for — but it means a late filter is not a way to make a view faster, and a total that includes something invisible needs explaining in a caption.

There is also a simpler tool for the same problem when you just want a column gone: right-click the header → Hide. Hiding keeps the data in the table calc's window too, and needs no calculation at all. Reach for a late filter when the rule is dynamic; reach for Hide when it isn't.

🕳️ Gaps in the data — the silent wrong answer

A table calculation walks the cells that exist. If March has no orders, there is no March cell — so "the previous month" for April is February, and a 3-month moving average covers four months of calendar time. Nothing warns you, and the line joins straight across the gap as though the month simply had normal sales.

  • Show Missing Values on the discrete date pill, or on a bin, inserts the empty members so offsets line up with the calendar
  • Nulls, not zeros. The padded cells are empty, so a moving average skips them rather than treating them as no sales. If zero is the honest value, wrap the measure in ZN()
  • Check any period-over-period number on sparse data — intermittent products, new stores, weekly data with holidays. This is where it bites hardest
  • The same problem hits histograms. An empty bin is not drawn, so the distribution's shape is wrong until you turn Show Missing Values on — see Bins

The general name for this is densification — Tableau filling in members that the data doesn't contain. It's genuinely useful here, and it's also why a view occasionally shows more marks than you expected: something in the view asked for padding. If a mark count looks inflated, check for a Show Missing Values you turned on earlier.

🔧 When the numbers look wrong

Everything shows 100% or 1

Compute Using is set to Cell. Each cell is its own window, so it's 100% of itself. Change the direction.

Percentages don't sum to 100%

Wrong direction. Decide what should total 100% — a row, a column, the table — and set Compute Using to match.

The first period is blank

Correct behaviour for any "vs previous" calc. There's nothing before the first row.

Numbers change when I filter

Also correct — table calcs only see the view. If you need percentages against the unfiltered total, you need an LOD expression instead.

Rearranging pills broke it

"Table (across)" is defined by layout, so moving pills changes it. Switch to Specific Dimensions to make the calc independent of arrangement.

Totals look wrong

Grand totals compute their own table calc rather than summing the displayed values. Analysis → Totals → Total All Using lets you control this.

A period-over-period number is off by a period

A gap in the data. The calc walked to the previous existing cell, not the previous month — see Gaps. Turn on Show Missing Values.

A second region continues the first one's running total

Region is addressed when it should be partitioning. Untick it under Specific Dimensions — see Addressing.

The pill won't go where I want it

A table calc is an aggregate, so it can't be used row-level, can't go in an LOD's dimension list, and can't be made a dimension. Compute it, then filter or label with it.

The debugging habit that works

Duplicate the sheet and switch it to a plain text table (Show Me → Text Table), with both the raw measure and the table calc side by side. Seeing the input and the output in the same grid makes the direction obvious immediately — far faster than staring at a line chart and guessing.

🧠 Key intuitions

  • Table calcs run on the view, not the data — so filtering changes their answers
  • They can't see filtered-out rows — by design
  • Compute Using is half the calculation — the function is the other half
  • The △ on a pill means a table calc is applied — always check for it
  • Always wrap an aggregate — SUM([Sales]), never bare [Sales]
  • Ask what should total 100% — then verify it does
  • "Percent" is half a question — always name the denominator out loud
  • Unticked dimensions are the "within"; ticked ones get summed into the denominator
  • TOTAL and WINDOW_SUM don't differ here — the partitioning is the lever
  • Ticked = walks along, unticked = starts over — that's the whole configuration
  • Specific Dimensions beats Table (across) — it survives layout changes
  • Restarting every is how a running total becomes year-to-date
  • A filter on a table calc runs last — it hides marks without changing the maths
  • Missing periods break offsets silently — Show Missing Values on sparse data
  • LOOKUP(…, -1) is "the previous one" — the basis of all period comparisons
  • Need it independent of filters? That's an LOD, not a table calc

🏆 Challenge: a Pareto chart

Show that a small share of sub-categories drives most of the sales. Sort sub-categories by Sales descending, add a running total of Sales as a percent of the overall total, and plot it as a line over the bars on a dual axis. Add a reference line at 80%. How many sub-categories does it take to reach it? If a handful of them account for most of the revenue, that is where attention and stock budget should go, and the rest of the range is a long tail you can treat differently. The whole chart is two table calculations stacked on each other: a running sum, expressed as a percent of total.
