🔬 LOD Expressions

Level of Detail expressions let a calculation aggregate at a different granularity than the view it sits in. They solve the problems that make people give up on Tableau — customer-level metrics inside a regional chart, percentages that ignore filters, cohort analysis. Each of those needs two levels of aggregation in one number, which nothing you have met so far can produce.

📖 Terms on this page

Defined before they're used. Every term on the site is also in the glossary.

Level of Detail (LOD)
The granularity a number is calculated at — how finely the data is cut before summing.
Example: The view might be per region while you need a figure computed per customer.
LOD expression
A calculation, written in curly braces, that aggregates at a different granularity than the view.
Example: {FIXED [Customer Name] : SUM([Sales])} — each customer's lifetime spend.
FIXED
Computes at exactly the dimensions you name, ignoring what's in the view.
Example: Stays per-customer even inside a regional chart. The predictable one.
INCLUDE
Starts from the view's granularity and goes finer.
Example: Average order size, computed per order then averaged at whatever level you're showing.
EXCLUDE
Starts from the view's granularity and goes coarser.
Example: A regional total displayed inside a chart broken down by category.
Cohort
A group defined by when they first appeared, tracked over time.
Example: Customers grouped by the year of their first order, to see whether they keep buying.

🧩 The problem LODs solve

Tableau aggregates to whatever dimensions are in your view. Put Region on Rows and you get four numbers. That's usually what you want — until it isn't.

A question you cannot answer without LODs

"What is the average customer's total spend, per region?"

You need to sum sales per customer first, then average those totals per region. Two levels of aggregation in one number. AVG([Sales]) gives you the average line item, which is a completely different — and much smaller — figure.

What AVG([Sales]) gives you
RegionAVG(Sales)

East$238

The average line item. Not what was asked.

→
What the LOD gives you
RegionAvg per customer

West$1,459

Total spend per customer, then averaged.

// Step 1 — a calculated field that sums per customer,
//          regardless of what's in the view
// Name: Customer Total
{ FIXED [Customer Name] : SUM([Sales]) }

// Step 2 — drop it on the view and set the aggregation to AVG
AVG([Customer Total])

📝 The syntax

{ KEYWORD [dimensions] : AGGREGATE(expression) }
  • { } Curly braces mark it as an LOD — always required
  • KEYWORD FIXED, INCLUDE or EXCLUDE
  • [dimensions] The granularity to aggregate at. Comma-separated; can be empty
  • : Separates the dimensions from the calculation
  • AGGREGATE(…) SUM, AVG, MIN, MAX, COUNTD — required, not optional
{ FIXED [Region] : SUM([Sales]) }
{ FIXED [Region], [Category] : SUM([Sales]) }   // two dimensions
{ FIXED : SUM([Sales]) }                     // no dimensions = grand total
{ INCLUDE [Customer Name] : SUM([Sales]) }
{ EXCLUDE [Category] : SUM([Sales]) }
Read it out loud

{ FIXED [Region] : SUM([Sales]) } reads as "the sum of sales, fixed at the region level". Whatever else is in the view, that number is computed per region and nothing else.

The three keywords on one scale

Every LOD does the same thing: it moves the calculation to a different point on the granularity scale. The only difference is how it picks the point.

  1. I
    INCLUDE — starts from wherever the view is and moves finer. Relative: change the view and it moves too.
  2. E
    EXCLUDE — starts from the view and moves coarser. Also relative.
  3. F
    FIXED — ignores the view entirely and computes at the level you named. Absolute, which is why it's the predictable one.
  4. ?
    Nothing here changes what is calculated — only the granularity it's calculated at.
Why FIXED is the one you'll reach for

INCLUDE and EXCLUDE are defined relative to the view, so the same expression means different things on different sheets — powerful, but harder to reason about. FIXED names an absolute level, so it computes the same number no matter what you drag around. Start with FIXED; use the other two when you specifically want the number to adapt.

📌 FIXED — ignore the view entirely

FIXED computes at exactly the dimensions you name and ignores every other dimension in the view. That makes it the one to reach for by default: the number it returns doesn't change when you rearrange the sheet.

What that unlocks

// Each category's share of ITS OWN region
SUM([Sales]) / MIN({ FIXED [Region] : SUM([Sales]) })

// Share of the grand total — no dimensions at all
SUM([Sales]) / MIN({ FIXED : SUM([Sales]) })

// A customer's lifetime value, usable at any level
{ FIXED [Customer Name] : SUM([Sales]) }

// The date each customer first ordered — the basis of cohort analysis
{ FIXED [Customer Name] : MIN([Order Date]) }

// How many orders has each customer placed?
{ FIXED [Customer Name] : COUNTD([Order ID]) }
Why the MIN() wrapper?

An LOD returns one value per group, but Tableau still needs an aggregate to combine it into the view. MIN, MAX and AVG all return the same answer here because every row in the group holds the identical value — MIN is just the convention. Omit it and you'll get "cannot mix aggregate and non-aggregate arguments".

➕ INCLUDE — go finer than the view

Adds dimensions to whatever is already in the view, computes there, then aggregates back up. Use it when you need a more detailed level than you're displaying.

// Average order size, shown at whatever level the view is at
AVG({ INCLUDE [Order ID] : SUM([Sales]) })

// Reads as: sum sales per order (plus whatever's in the view),
// then average those order totals.
INCLUDE vs FIXED — the practical difference

INCLUDE adapts to the view: drag Region in and it computes per order within each region. FIXED ignores the view entirely. If you want a number that responds to how you slice the dashboard, use INCLUDE; if you want a constant reference value, use FIXED.

➖ EXCLUDE — go coarser than the view

Removes dimensions from the view's granularity. The classic use is showing a total alongside its own breakdown.

// Regional total, displayed in a view broken down by Category
{ EXCLUDE [Category] : SUM([Sales]) }

// Each category's share of its region — an alternative to the FIXED version
SUM([Sales]) / MIN({ EXCLUDE [Category] : SUM([Sales]) })

// How far is this month above or below the yearly average?
SUM([Sales]) - AVG({ EXCLUDE [Month of Order Date] : SUM([Sales]) })

EXCLUDE is relative — it strips named dimensions from whatever's in the view. That makes it flexible but harder to reason about, which is why most people reach for FIXED. Both are correct; FIXED is easier to debug.

🌐 The table-scoped LOD — braces and nothing else

There is a fourth form, and it has no keyword at all:

{ SUM([Sales]) }              // a table-scoped LOD
{ FIXED : SUM([Sales]) }      // exactly the same thing, spelled out
{ MAX([Order Date]) }         // the latest date anywhere in the data
{ COUNTD([Customer Name]) }  // how many customers exist, full stop

With no dimensions to group by, it computes over the whole table and hands the same number to every row. That makes it the natural way to write "compared to everything" — a share of the company total, a distance from the overall average, a benchmark line that doesn't move.

Where the short form earns its keep

{MAX([Order Date])} is the workhorse. Point a parameter's Value when workbook opens at it and the dashboard always opens on the latest date in the data; use it as a relative date filter's anchor and "last 12 months" means the last twelve months of data rather than of the calendar. Both fix the problem where a workbook looks broken because the data hasn't caught up with today.

Like every FIXED, it ignores dimension filters — so it stays constant as viewers filter, which is usually the point. If you need it to follow a filter, add that filter to context.

🧱 An LOD returns a row-level value — and that changes what you can do with it

This is the part that isn't obvious from the syntax. {FIXED [Customer Name] : SUM([Sales])} doesn't produce a little table off to one side. It computes a number per customer and then attaches that number to every row belonging to that customer. Each of Sarah Bern's fourteen order lines carries her $2,400 lifetime total.

Because the result exists at row level, an LOD can be used everywhere a real column can:

Inside row-level logic

IF { FIXED [Customer Name] : SUM([Sales]) } > 5000
THEN "VIP" ELSE "Standard" END

No MIN() needed — you're comparing row-level things to each other.

Converted to a dimension

Drag the LOD field up into Dimensions, or right-click → Convert to Dimension. It becomes a discrete field you can slice by, sort, colour and — the useful part — tick in a filter list.

On the Filters shelf

Choose All values at the aggregation prompt and it filters raw rows: "only customers who have ever spent over $5,000", and it stays true however you slice the view.

As a bin

Right-click → Create → Bins on a customer-total LOD and you get a distribution of customers by lifetime spend — a histogram the raw data can't produce.

Choosing the outer aggregation is a real decision, not a formality

Because the value is attached to rows, dropping it in a view forces you to pick how to combine it — and each choice answers a different question:

In a view broken down by RegionAnswers
AVG({FIXED [Customer] : SUM([Sales])})What does a typical customer here spend?
MAX({FIXED [Customer] : SUM([Sales])})How big is the biggest customer here?
SUM({FIXED [Customer] : SUM([Sales])})Total spend of these customers — and the one to check hardest

None of them errors. If a total comes out implausibly large, the usual cause is summing a value that is repeated across many rows. Always compare the number against one you already trust — the $2,297,201 Superstore total is there precisely for this.

When the LOD's dimensions are coarser than or equal to the view — {FIXED [Region] : …} in a Region × Category view — every row in a mark carries the identical number, so MIN, MAX and AVG all return it. That's the case the MIN() convention was invented for, and it's why you see it everywhere.

🪜 Order of operations — where FIXED surprises people

Tableau evaluates things in a fixed sequence. FIXED is computed before dimension filters, which is either exactly what you want or a nasty surprise.

  1. Extract filters
    Applied when the data was extracted
  2. Data source filters
    Set on the connection
  3. Context filters
    Right-click a filter → Add to Context. These DO affect FIXED.
  4. FIXED LOD expressions — and sets, Top N filters, conditional filters
    All computed here, before ordinary filters. Same rung, same surprises
  5. Dimension filters
    Your normal filter cards. FIXED ignores these.
  6. INCLUDE / EXCLUDE LODs
    Computed after dimension filters, so they respect them
  7. Measure filters
    Filters on aggregated values
  8. Forecasts and clusters
    Fitted to whatever survived the filters above
  9. Table calculations, and filters placed on them
    Run last, on the finished view — see the full ladder
  10. Trend lines, reference lines, totals
    Computed from the marks that remain

The ordinary SUM drops to the West total. The FIXED expression does not budge, because step 4 happens before step 5. Sometimes that's exactly what you want — it's how you compute “West as a share of the whole company”.

⚠️ When you need FIXED to respect a filter

Context filters run at step 3, ahead of FIXED at step 4 — so promoting a filter to context is the one way to make a FIXED expression see it. Right-click the Region filter → Add to Context, and the grand total drops to West's $725,458.

Leave it alone when the unfiltered number is the point, as it is for "what share of company-wide sales is West?"

✓ Want the LOD to ignore filters

Use FIXED and leave the filters alone. Good for "% of company total" or a constant benchmark line.

✓ Want the LOD to respect filters

Either add the filter to Context, or use INCLUDE / EXCLUDE, which sit after dimension filters in the sequence.

🪢 Nesting, and the things LODs can't do

LODs nest. The inner expression is evaluated first and its result becomes an input to the outer one — which is how you write "the average customer's spend, per region, as a single field" instead of relying on the pill's aggregation.

// Average customer spend, computed per region and fixed there
{ FIXED [Region] : AVG({ FIXED [Customer Name] : SUM([Sales]) }) }

// Each customer's share of their own region's revenue
{ FIXED [Customer Name] : SUM([Sales]) }
  / { FIXED [Region] : SUM([Sales]) }

// Days between a customer's first and last order
DATEDIFF('day',
  { FIXED [Customer Name] : MIN([Order Date]) },
  { FIXED [Customer Name] : MAX([Order Date]) })

Each level has its own dimension list and they are independent — the outer one does not inherit the inner one's. Read a nested LOD from the inside out and it stays legible; write one from the outside in and it usually doesn't.

What an LOD cannot do

LimitationWhat to do instead
Can't contain a table calculation, and can't appear inside one's dimension listThey run at different stages of the pipeline. Compute the LOD first, then apply the table calc to it
Can't do anything positional — running total, rank, "the previous row"That's a table calculation, always
FIXED isn't available on the secondary source of a data blendUse a relationship or a join instead of a blend, or pre-aggregate the secondary source
COUNTD inside an LOD is expensive on large sourcesFine on Superstore. On tens of millions of rows, extract and pre-aggregate
The dimension list takes dimensions only — not measures, not aggregatesWrap the thing you want to group by in a calculated field that returns a dimension first
LODs are computed by the database, and that cuts both ways

Because Tableau pushes them into the query, an LOD over millions of rows is usually faster than the equivalent table calculation — the work happens where the data lives. But several nested LODs, or a COUNTD inside one, can generate a genuinely heavy query. If a workbook slows down sharply after you add an LOD, that's where to look first, and materialising an extract is normally the cheapest fix.

⚖️ LOD or table calculation?

They overlap, and choosing wrongly is the source of a lot of frustration. The deciding question: does the number need to see data that isn't in the view?

AspectLOD expressionTable calculation
Where it runsIn the database, before the viewOn the finished view, in Tableau
Can see rows not in the view✓ Yes✗ No
Affected by dimension filtersFIXED: no · INCLUDE/EXCLUDE: yesAlways yes
Depends on view layout✓ No — stableYes — Compute Using
Running totals, rank, moving avg✗ Can't✓ Built for it
Different granularity than the view✓ Built for it✗ Can't

The rule of thumb

Anything positional — running total, rank, "compared to the previous row", moving average — is a table calculation. Anything about granularity — per customer, per order, ignoring a filter — is an LOD.

📖 Recipes worth memorising

Customer cohort analysisGroup customers by when they first bought
// Acquisition date — the customer's first ever order
{ FIXED [Customer Name] : MIN([Order Date]) }

// Cohort year — turn that into a grouping dimension
YEAR({ FIXED [Customer Name] : MIN([Order Date]) })

// Is this order the customer's first?
IF [Order Date] = { FIXED [Customer Name] : MIN([Order Date]) }
THEN "New" ELSE "Returning" END

Put Cohort Year on Rows and Order Year on Columns and you have a retention grid — the analysis every subscription business runs, and it's three lines of calculation.

Customer segmentationClassify by total behaviour, not per row
// Bucket customers by lifetime spend
IF { FIXED [Customer Name] : SUM([Sales]) } > 5000 THEN "VIP"
ELSEIF { FIXED [Customer Name] : SUM([Sales]) } > 1000 THEN "Regular"
ELSE "Occasional"
END

// Repeat customers only
{ FIXED [Customer Name] : COUNTD([Order ID]) } > 1

Because it's FIXED, the segment stays stable no matter how you slice the view — a customer doesn't stop being a VIP because you filtered to one region.

Percent of total that ignores filtersThe table-calc problem, solved
// Share of company-wide sales, even when filtered
SUM([Sales]) / MIN({ FIXED : SUM([Sales]) })

// Compare with the table-calc version, which uses only
// what survived the filters:
SUM([Sales]) / TOTAL(SUM([Sales]))

Put both on the same view with a filter active: the LOD version's percentages stay small because they're still measured against all $2.3M, while the table-calc version's re-scale to sum to 100% across whatever survived the filter. Which is "right" depends on whether the reader is asking "how big is this within the selection?" or "how big is this within the company?"

Comparison against a benchmarkEvery row measured against a constant
// How does this sub-category compare to the overall average?
SUM([Profit]) - MIN({ FIXED : AVG([Profit]) })

// Above or below its own region's average?
SUM([Sales]) - MIN({ FIXED [Region] : AVG([Sales]) })

// Percent of the best-performing region
SUM([Sales]) / MAX({ FIXED [Region] : SUM([Sales]) })

🧠 Key intuitions

  • An LOD changes the granularity a number is computed at — nothing else
  • FIXED ignores the view; INCLUDE goes finer; EXCLUDE goes coarser
  • Read it as a sentence — "sum of sales, fixed at customer level"
  • FIXED runs before dimension filters — Context filters are how you override that
  • Wrap LODs in MIN/MAX/AVG when combining them with other aggregates
  • Positional → table calc, granularity → LOD
  • {FIXED : …} with no dimensions is a grand total that survives filtering
  • FIXED makes segments stable — a VIP stays a VIP whatever you filter to
  • { SUM([Sales]) } with no keyword is a table-scoped LOD — the grand total
  • An LOD is a row-level value — so it can be a dimension, a bin or a row-level filter
  • The outer aggregation is a decision — AVG, SUM and MAX ask different questions
  • LODs nest; read them inside out

🏆 Challenge: are we growing by acquiring or by keeping?

Build a view splitting each year's revenue into new-customer revenue and returning-customer revenue, using a FIXED acquisition date to classify each order. Then answer the question a board actually cares about: is revenue growth coming from customers we already had, or from ones we bought? Add the count of distinct customers per cohort and you can see retention decay directly. The whole analysis rests on one expression — {FIXED [Customer Name] : MIN([Order Date])} — because every order needs to know a fact computed at customer level, which is precisely what the view's own granularity cannot give you.
