🧮 Calculated Fields

New data derived from existing fields. Ratios, categories, date maths, conditional logic — this is where Tableau stops being limited to the columns you were given and starts answering the questions you actually have.

📖 Terms on this page

Defined before they're used. Every term on the site is also in the glossary.

Calculated field
A new field you define with a formula. It joins the Data pane like any other.
Example: SUM([Profit])/SUM([Sales]) saved as Profit Margin.
📍 Analysis → Create Calculated Field
Row-level calculation
Runs once per row of the source data, before aggregation.
Example: [Profit]/[Sales] computes a margin for each of the 9,994 line items.
Aggregate calculation
Runs on already-totalled numbers. Nearly always what you want for ratios.
Example: SUM([Profit])/SUM([Sales]) gives West 14.9%; the row-level version gives 4.2%.
Null
A missing value — not the same as zero.
Example: A blank Sales cell means "unknown"; zero means "sold nothing".
ZN
A function that turns Null into 0.
Example: ZN([Profit]). Convenient, and often the wrong choice — decide deliberately.
Parameter
A single value the viewer can change, which calculations can read.
Example: A "Sales Threshold" slider that recolours a chart as you move it.

✏️ Creating a calculated field

Three routes to the same dialog: Analysis → Create Calculated Field, right-click in the Data pane, or the dropdown on any field → Create → Calculated Field.

NameProfit Margin
SUM([Profit]) / SUM([Sales])
✓ The calculation is valid. Apply   OK

Tableau validates as you type. Red means it won't save — and the message underneath usually tells you exactly what's wrong.

Syntax essentials

  • Field names go in [square brackets]
  • Text uses "double quotes"
  • Date parts use 'single quotes'
  • // starts a comment
  • Function names are case-insensitive; field names are not

Habits worth forming

  • Name fields for what they mean, not how they're built
  • Comment anything non-obvious — you will forget
  • Break long logic into several small fields
  • Use the right-hand panel to look up functions
Ad-hoc calculations — a formula without a field

Double-click an empty part of any shelf and type a formula directly. Press Enter and you get a working pill with no entry in the Data pane. Perfect for a one-off MIN(0) placeholder or a quick SUM([Sales])-SUM([Profit]) you're only testing.

Changed your mind and want to keep it? Drag the pill from the shelf into the Data pane and it becomes a real calculated field, name and all. Working this way keeps the Data pane clean, which matters more than it sounds once a workbook has forty calculations in it.

Two things worth finding in the editor: the function reference on the right, which shows the syntax and an example for every function; and the ▾ at the top right, which lists this calculation's dependencies and what depends on it. The second is how you find out whether deleting something will break three sheets.

🔠 Data types — and converting between them

Every field and every expression has a type: string, number (integer or decimal), date, date & time, or boolean. Tableau does almost no implicit conversion, so a surprising share of "the calculation won't save" is a type mismatch rather than a logic error. The message usually names both types, which tells you exactly which side to convert.

// Number ⇄ text
INT([Sales])          // 261.96 → 261. Truncates toward zero — it does NOT round
ROUND([Sales], 0)    // 261.96 → 262. Use this when you meant to round
FLOAT([Quantity])     // forces decimal division: FLOAT(a)/b
STR([Year])           // 2017 → "2017", so you can concatenate it

// Text → date
DATE([Order Date])                          // works when the text is unambiguous
DATEPARSE("dd/MM/yyyy", [Raw Date])       // when it isn't — you supply the pattern

// Building a date from parts
MAKEDATE(2017, 11, 9)
MAKEDATETIME([Order Date], [Order Time])

// Boolean → number, for counting
INT([Profit] < 0)     // True → 1, False → 0. SUM() it to count loss-makers
Three type traps worth knowing before you meet them
  • Integer division truncates. [Quantity]/[Orders] with two integers can return 0. Wrap one side in FLOAT().
  • DATEPARSE isn't available on every connection. If it's missing or errors, extract the data first — it works on extracts regardless of source.
  • Comparisons are case-sensitive. [Region] = "east" matches nothing. Use UPPER() on both sides, or fix it at the source.

A calculation's own type decides where it lands: return a number and it goes to Measures; return text, a date or a boolean and it goes to Dimensions. That's why SUM([Profit])/SUM([Sales]) arrives green and IF … THEN "High" arrives blue — and it's also what decides which filter dialog you get when you drag it onto Filters.

⚠️ Row-level vs aggregate — the distinction that matters

Every calculation runs either on each row of the data or on the aggregated numbers in your view. Mixing them is the most common error in Tableau, and for ratios it produces genuinely wrong answers rather than errors.

Row-level, then averaged
AVG([Profit] / [Sales])

Computes a margin for every line item, then averages those percentages. A $5 order counts as much as a $5,000 one.

West region: 4.2%

→
Aggregate, then divided
SUM([Profit]) / SUM([Sales])

Totals both columns first, then divides. Every dollar weighted equally — the actual margin.

West region: 14.9%

Follow the arithmetic

Two rows of data, two computation paths, two different answers. Both look reasonable on screen.

The gap widens as your rows get more uneven. On real Superstore data the two answers differ by roughly 3×.

Neither errors — and they differ by a factor of three

For any ratio — margin, conversion rate, cost per unit — you almost always want SUM(a) / SUM(b), not AVG(a/b). The row-level version is an average of percentages, which weights a tiny order the same as an enormous one. It's the single most common way a Tableau dashboard ends up quietly reporting the wrong number.

// ✗ Won't even save — mixing the two
SUM([Profit]) / [Sales]
//   "Cannot mix aggregate and non-aggregate arguments"

// ✓ Both aggregated
SUM([Profit]) / SUM([Sales])

// ✓ Both row-level — Tableau aggregates the result later
[Profit] / [Sales]

A row-level field appears in the Data pane as a measure you can aggregate however you like. An aggregate calculation is already aggregated — you can't change it with the pill dropdown. That's a useful way to tell which you wrote.

✳️ ATTR — and where the asterisk comes from

Sooner or later a tooltip or a label shows * instead of a value, and nothing explains it. That asterisk is Tableau telling you something specific and useful: this mark contains more than one value of that field, so there is no single answer to show.

One mark, one value
RegionCountrySales
WestUnited States725,458

Every row inside the West mark has the same Country, so ATTR([Country]) can show it.

→
One mark, several values
RegionStateSales
West*725,458

The West mark spans 13 states. There is no one state to print, so you get *.

// What ATTR actually does — this is the whole definition
ATTR([State])

// is equivalent to
IF MIN([State]) = MAX([State])
THEN MIN([State])
ELSE "*"
END

Why it exists at all

Tableau can only put aggregates into a view alongside other aggregates. A dimension isn't an aggregate — so when you drop one somewhere that needs one (a tooltip on a coarser view, one side of a dual axis, the secondary table of a blend), Tableau silently wraps it in ATTR. It's the "give me the value if there's only one, and admit it otherwise" aggregation.

You seeWhat it meansWhat to do
* in a tooltip or labelThe mark spans several values of that fieldAdd the field to the view's level of detail, or accept it and describe the mark differently
ATTR(…) appearing on a pill you didn't writeTableau needed an aggregate and chose the safe oneUsually fine. Swap for MIN or MAX if you genuinely want one of the values
A blend showing * everywhereThe secondary source is coarser than the viewAdd the linking field to the view, or aggregate the secondary source first
Treat the asterisk as information, not an error

It is Tableau refusing to pick one value arbitrarily, which is the honest behaviour. MIN([State]) in the same place would print "Arizona" for a mark covering thirteen states — no asterisk, and a chart that is quietly lying. When you see *, the right question is "what grain is this mark actually at?", not "how do I make it go away".

➗ Basic calculations

// Ratios — aggregate both sides
SUM([Profit]) / SUM([Sales])           // profit margin
SUM([Sales]) / COUNTD([Order ID])       // average order value
SUM([Sales]) / SUM([Quantity])         // price per unit

// Row-level maths
[Sales] * (1 - [Discount])              // revenue after discount
[Sales] - [Profit]                       // cost of goods

// Aggregation functions
SUM()  AVG()  MIN()  MAX()  MEDIAN()
COUNT()      // number of rows
COUNTD()     // number of DISTINCT values
STDEV()  VAR()

// Rounding and absolutes
ROUND([Sales], 2)
ABS([Profit])
CEILING([Sales])   FLOOR([Sales])
COUNT vs COUNTD on Superstore

Each row is one line item, so COUNT([Order ID]) returns 9,994 — the number of lines, not orders. COUNTD([Order ID]) returns 5,009, the actual number of orders. Reporting the first as "orders" overstates it by roughly 2×, and it's an easy mistake to ship.

🔀 Conditional logic

IF — for conditions

// Basic
IF [Profit] > 0 THEN "Profitable"
ELSE "Loss"
END

// Several branches
IF [Sales] > 1000 THEN "High"
ELSEIF [Sales] > 500 THEN "Medium"
ELSE "Low"
END

// IIF — compact, two outcomes
IIF([Profit] > 0, "Profit", "Loss")

CASE — for exact matches

CASE [Region]
  WHEN "East"  THEN "Coastal"
  WHEN "West"  THEN "Coastal"
  ELSE "Inland"
END

// Assign a custom sort order
CASE [Ship Mode]
  WHEN "Same Day"     THEN 1
  WHEN "First Class"  THEN 2
  WHEN "Second Class" THEN 3
  ELSE 4
END

If you wrote Sales > 500 first, every order above 1000 would also pass it and be labelled "Medium" — the "High" branch would never fire.

CASE when you can, IF when you must

CASE is faster and far more readable, but it only compares one field against exact values. Anything involving ranges, multiple fields, or AND/OR needs IF. The sort-order example above is how you get Ship Mode to sort by speed rather than alphabetically: the CASE returns a number, and you sort the dimension by that field instead of by its own name.

Combining conditions

// AND / OR / NOT
IF [Profit] > 0 AND [Discount] = 0 THEN "Clean sale"
ELSEIF [Profit] < 0 AND [Discount] > 0.2 THEN "Over-discounted"
ELSE "Normal"
END

// IN — cleaner than a chain of ORs
IF [Region] IN ("East", "West") THEN "Coastal" ELSE "Inland" END

// A boolean field — returns True/False directly, no IF needed
[Profit] < 0

📅 Date calculations

// Difference between two dates
DATEDIFF('day', [Order Date], [Ship Date])     // days to ship
DATEDIFF('month', [Order Date], TODAY())     // months ago

// Extract parts
YEAR([Order Date])                  // 2017
MONTH([Order Date])                 // 11 — a number
DATENAME('month', [Order Date])    // "November" — text
DATEPART('quarter', [Order Date])  // 4

// Truncate to the start of a period — keeps it a real date
DATETRUNC('month', [Order Date])   // 1 Nov 2017
DATETRUNC('quarter', [Order Date])

// Shift a date
DATEADD('month', 3, [Order Date])
DATEADD('year', -1, [Order Date])     // same date last year

// Is it in the current year?
YEAR([Order Date]) = YEAR(TODAY())
DATETRUNC vs DATENAME

DATETRUNC returns a date — it sorts and charts correctly. DATENAME returns text, so "April" sorts before "January". Use DATETRUNC for anything on an axis, and DATENAME only for labels.

✂️ Text functions

// Extract
LEFT([Order ID], 2)                // "CA"
RIGHT([Order ID], 6)               // "152156"
MID([Order ID], 4, 4)              // "2016"

// Transform
UPPER([Category])   LOWER([Category])   PROPER([City])
TRIM([Customer Name])              // strip stray spaces
LEN([Product Name])                // character count

// Search and test
CONTAINS([Product Name], "Chair")  // True / False
STARTSWITH([Order ID], "CA")
FIND([Order ID], "-")               // position of first dash
REPLACE([Country], "United States", "USA")

// Combine — + concatenates in Tableau, not &
[City] + ", " + [State]

// Splitting on a delimiter — the number is which part, counting from the left
SPLIT([Order ID], "-", 2)             // "2016"

You can often skip the calculation entirely: right-click a field in the Data pane → Split or Custom Split. Tableau writes the fields for you and they're easier to maintain.

🕳️ Handling nulls

// ZN — turn Null into zero
ZN([Profit])

// IFNULL — substitute anything
IFNULL([Region], "Unknown")

// ISNULL — test for it
IF ISNULL([Customer Name]) THEN "Missing" ELSE [Customer Name] END

// Guard against divide-by-zero — Tableau returns Null, not an error
IF SUM([Sales]) = 0 THEN NULL
ELSE SUM([Profit]) / SUM([Sales]) END

How nulls move through logic

A comparison with a null is neither true nor false — it's unknown. That has a specific and easily-missed consequence in IF: a null falls through to ELSE, silently joining whatever bucket you meant for something else.

// A null Profit is not > 0, so it lands in "Loss"
IF [Profit] > 0 THEN "Profitable" ELSE "Loss" END

// Test for it explicitly, first
IF ISNULL([Profit]) THEN "Unknown"
ELSEIF [Profit] > 0 THEN "Profitable"
ELSE "Loss" END

// An IF with no ELSE returns Null when nothing matches — often what you want
IF [Profit] < 0 THEN [Sales] END   // sales of loss-making lines only

Aggregations skip nulls rather than failing: AVG of 10, null, 20 is 15, not 10. COUNT counts non-null values only, which is why COUNT([Profit]) can be smaller than the number of rows. That's usually the behaviour you want — but it means a field quietly full of nulls produces confident-looking averages over far fewer rows than you think.

Null is not zero — decide deliberately

ZN() is convenient and often wrong. A missing sales figure means "we don't know"; zero means "they bought nothing". AVG skips nulls but counts zeros, so converting them silently drags your averages down. Only use ZN when zero is genuinely the right answer.

🎛️ Parameters — let the viewer decide

A parameter is a single value a user can change. On its own it does nothing — it isn't tied to any field and filters nothing. It only has an effect once a calculation, a filter or a reference line reads it, and then whatever reads it responds live as the viewer changes the value.

  1. Create the parameter

    Right-click in the Data pane → Create Parameter. Name it Threshold, type Float, and set a range.

  2. Use it in a calculation

    IF [Sales] > [Threshold] THEN "Above" ELSE "Below" END

  3. Show the control

    Right-click the parameter → Show Parameter. A slider or input box appears beside the view.

  4. Drag the calculation onto Color

    Now moving the slider re-colours the whole chart live. That's a "what if" analysis in four steps.

A parameter list is a snapshot, and that is how dashboards go stale

"Add values from field" copies the members that exist right now. Add a fifth region next year and the parameter still offers four, with nothing on screen to say so. Any parameter listing real data values needs List of values when workbook opens pointed back at the field — otherwise you have signed up to maintain it by hand.

The refresh happens when the workbook opens or the extract refreshes. A viewer sitting on a dashboard for an hour will not see new values arrive.

Parameters are single-value and workbook-wide

One value at a time — there is no multi-select parameter, which is why "let them pick several metrics" is a job for Measure Names on Filters instead. And a parameter belongs to the workbook, not to a data source: one parameter can drive charts built on three different connections at once, which is something no filter can do.

🔌 What a parameter can drive

A parameter is inert until something reads it. These are the seven places that can, and between them they cover nearly every interactive dashboard you have admired.

Read byGives you
A calculated fieldAnything at all — the swappers and what-ifs below
A filter's Top tabViewer-chosen Top N, with no calculation
A filter's Condition tab"Only sub-categories above the threshold I set"
A reference line's ValueA draggable target line — instant what-if
A bin's sizeA histogram whose bucket width the reader controls
A relative date filter's anchorAn "as of" date for the whole workbook, set in one place
A title, caption or tooltip<Parameters.Select Measure> — so the chart says which metric it is showing

The two swappers

Measure swapper

// String list: Sales / Profit / Quantity / Discount
CASE [Select Measure]
  WHEN "Sales"    THEN SUM([Sales])
  WHEN "Profit"   THEN SUM([Profit])
  WHEN "Quantity" THEN SUM([Quantity])
  ELSE AVG([Discount])
END

Drop it on Rows. One chart, four questions — a dashboard that would need four sheets needs one.

Dimension swapper

// String list: Region / Category / Segment
CASE [Break Down By]
  WHEN "Region"   THEN [Region]
  WHEN "Category" THEN [Category]
  ELSE [Segment]
END

Returns text, so it lands in Dimensions and slices the view. Every branch must return the same data type.

Two things to fix on any swapper

Number format: the branches return different units, so a single field-level format is always wrong for three of them. Set the format on the sheet, or add a matching parameter-driven format. Titles: insert <Parameters.Select Measure> into the title, otherwise a screenshot of the dashboard says nothing about which metric it shows.

Parameter Actions — set the value by clicking

Dashboard → Actions → Change Parameter. Clicking a mark writes a field's value into a parameter. Click a region on a map and every other chart rebases to it; click a bar to set the comparison baseline; click a month to move an "as of" date. It removes the dropdown entirely — the chart is the control.

Pair it with a set action and you have the two ways a click can change the state of a dashboard: a parameter carries one value, a set carries a membership.

Parameter vs filter, in one line: a filter chooses which rows survive; a parameter supplies a value. If the viewer is picking from things that exist in the data, that's usually a filter. If they're supplying something the data doesn't contain — a target, a rate, a scenario — it has to be a parameter.

🧠 Key intuitions

  • Ratios use SUM(a)/SUM(b), never AVG(a/b)
  • You can't mix aggregate and row-level in one expression
  • COUNTD for orders, COUNT for line items
  • CASE for exact matches, IF for everything else
  • DATETRUNC keeps it a date; DATENAME makes it text
  • Null ≠ zero — ZN() is a decision, not a cleanup
  • + concatenates text in Tableau, not &
  • Name fields for meaning, and comment the non-obvious
  • Parameters + CASE = one chart, many questions
  • A parameter does nothing until something reads it
  • Parameter lists are snapshots — set "list of values when workbook opens"
  • * means the mark spans several values — that's ATTR being honest
  • Nulls fall through to ELSE — test for them first if it matters
  • Integer division truncates — wrap one side in FLOAT()

🏆 Challenge: an order quality score

Build a score from several criteria — 3 points for profit over $100, 2 for no discount, 1 for fast shipping — then bucket the total into Excellent / Good / Poor. Colour a scatter of Sales vs Profit by that score. The interesting part isn't the calculation; it's deciding what deserves points and defending it. Then check whether high-scoring orders cluster anywhere: a particular segment, region, or category. A cluster means the score is picking up something structural about the business rather than just re-describing profit.
